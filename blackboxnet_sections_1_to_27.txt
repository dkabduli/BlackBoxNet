# 1. PRODUCT IDENTITY

## Product Name
**BlackBoxNet**

## Product Positioning
A network “flight recorder” and replay system that helps engineers answer:

- What changed before the outage?
- What config change likely caused the failure?
- What was the last known healthy state?
- How did the network degrade over time?

## One-Line Description
BlackBoxNet is a time-indexed network state replay platform that records configuration snapshots, health metrics, and network events, then reconstructs a failure timeline so engineers can identify what changed before an outage.

## Phase 1 Identity
Phase 1 is a **simulation-driven MVP**.  
It is not a production network polling system yet.

It must prove these product truths:

1. Time-indexed network state is useful
2. Git-backed config history adds value
3. Timeline replay helps explain failures
4. Simple rules-based correlation can highlight suspicious changes before outages

---

# 2. TARGET USER

## Primary User
Junior network engineer or networking lab user

## User Context
This user:
- applies or studies Cisco-like or Juniper-like configs
- causes or encounters outages due to misconfiguration
- does not yet have deep intuition for config blast radius
- wants to understand what changed before the outage

## Core User Story
> “My network broke after a config change. I want to see what changed, when it changed, and what likely caused the outage.”

---

# 3. PROBLEM STATEMENT

Current tooling is fragmented:

- config backup/versioning tools show config diffs but not network impact
- monitoring tools show symptoms but not config context
- logs are scattered
- junior engineers struggle to connect cause and effect

There is no simple, replayable timeline that combines:
- config history
- device health
- interface state
- outage progression

BlackBoxNet aims to bridge this gap.

---

# 4. PHASE 1 PRODUCT GOAL

## Goal
Build a web application that simulates a small network, records its state over time, stores config versions in Git, stores metrics/events in a database, and lets the user replay one realistic outage scenario.

## Success Criteria
A user can:
1. View three network devices
2. View an incident
3. Open a chronological timeline
4. See the exact config diff that occurred before degradation
5. See health and interface degradation after the config change
6. Read a rules-based suspicion statement linking the change to the outage

---

## In Scope
- mocked devices only
- pre-scripted scenario only
- Git-backed config snapshots
- simulated metrics and state changes
- event generation
- incident timeline

## Out of Scope

- production-scale topology support

# 6. HIGH-LEVEL PRODUCT CONCEPT

BlackBoxNet acts like a **central observer**.

In production, this would sit on a server and poll devices.  
In Phase 1, it runs locally and consumes scripted network state from mock devices.

Core loop:
1. ingest device state at each time step
2. store config and metrics
3. detect changes
4. emit events
5. build incident timeline
6. correlate suspicious recent changes
7. visualize replay

# 7. PHASE 1 NETWORK TOPOLOGY

The MVP must simulate a realistic, small enterprise/lab topology with three devices.

## Device 1: edge-router-1
- role: L3 edge / policy enforcement point
- vendor style: Cisco IOS-like in Phase 1
- primary function:
  - routes between connected segments
  - has inbound ACL applied on internal-facing interface
- example internal-facing subnet:
  - 10.0.0.0/24
- downstream subnet affected by ACL logic:
  - 10.0.1.0/24

## Device 2: dist-switch-1
- role: distribution switch
- uplink between router and access layer
- simplified behavior:
  - forwards traffic
  - may expose interface state and latency effects
- vendor style:
  - can still be represented with Cisco-like state in Phase 1

## Device 3: access-switch-1
- role: access layer switch
- represents the edge of the affected user subnet
- downstream logical subnet:
  - 10.0.1.0/24

## Logical Traffic Story
Traffic originating from 10.0.1.0/24 should normally be permitted through the router.  
A config change on edge-router-1 introduces an ACL that blocks this subnet.  
The simulated system should then show progressive degradation:
- increased latency
- errors or degraded interface state
- eventual outage/unreachability for affected traffic

---

# 8. PHASE 1 OUTAGE SCENARIO

Phase 1 uses one pre-scripted, deterministic incident.

## Scenario Name
**ACL Regression Blocks Downstream Subnet**

## Timeline
### T1 — Healthy Baseline
- all devices healthy
- router config permits all relevant traffic
- latency nominal
- interfaces up
- no outage

### T2 — Config Change
- ACL on edge-router-1 changes
- old config allows traffic
- new config denies traffic from 10.0.1.0/24 before broader permit
- config hash changes
- Git commit created
- CONFIG_CHANGE event emitted

### T3 — Degradation Begins
- traffic from downstream subnet begins to fail
- latency increases
- packet retries simulated
- LATENCY_SPIKE event emitted

### T4 — Interface/Resource Stress
- interface state remains up but error counters or degraded state increases
- CPU rises slightly on edge-router-1 or dist-switch-1
- INTERFACE_DEGRADED or INTERFACE_ERRORS event emitted

### T5 — Outage
- affected subnet becomes unreachable or packet loss reaches outage threshold
- OUTAGE event emitted
- incident marked active

This scenario must be deterministic and replayable.

# 9. CONFIGURATION SEMANTICS

Phase 1 should use **realistic network configuration semantics**, even though configs are mocked.

## 9.1 Primary Vendor Syntax for Phase 1
Primary simulated syntax should be **Cisco IOS/IOS-XE style**.

Reason:
- clear line-based running-config format
- straightforward ACL semantics
- easier line diffing for phase one
- intuitive for networking labs

## 9.2 Future Vendor Support
The architecture must anticipate future support for:
- Cisco IOS/IOS-XE
- Juniper Junos
- Nokia SR OS

But Phase 1 should only need one enforced vendor syntax for the active scenario.

## 9.3 Baseline Cisco-Like Router Config
The Phase 1 baseline should resemble this logic:

```text
hostname edge-router-1

interface GigabitEthernet0/0
 description LAN-facing interface
 ip address 10.0.0.1 255.255.255.0
 ip access-group 100 in
 no shutdown

interface GigabitEthernet0/1
 description Uplink
 ip address 192.168.1.1 255.255.255.0
 no shutdown

access-list 100 permit ip any any
```

## 9.4 Fault-Inducing Cisco-Like Router Config
The faulty config should resemble this logic:

```text
hostname edge-router-1

interface GigabitEthernet0/0
 description LAN-facing interface
 ip address 10.0.0.1 255.255.255.0
 ip access-group 101 in
 no shutdown

interface GigabitEthernet0/1
 description Uplink
 ip address 192.168.1.1 255.255.255.0
 no shutdown

access-list 101 deny ip 10.0.1.0 0.0.0.255 any
access-list 101 permit ip any any
```

## 9.5 Semantic Meaning
This config change must be interpreted by the system as:
- a new ACL is now attached to the interface
- the ACL denies traffic from 10.0.1.0/24
- all other traffic is permitted
- connectivity for the downstream subnet should degrade/fail after this change

## 9.6 Phase 1 Config Intelligence Expectations
Phase 1 does not need a full parser for all Cisco syntax, but it should be designed so that:

- configs are stored as raw text
- line diffs are supported
- key semantic extraction is possible for the scenario:
  - interface ACL attachment
  - ACL rule additions/removals
  - deny-before-permit pattern
  - subnet references

Claude should preserve this line:
**Phase 1 needs scenario-specific semantic extraction, not a full production config parser.**

# 14. GIT STRATEGY

This product must use **real Git** in Phase 1 for config history.

## 14.1 Why Git is Required
- gives meaningful config version history
- enables future branching/rollback concepts
- reinforces the “black box for config history” concept
- makes diffs intuitive and developer-friendly

## 14.2 Repo Layout
Suggested:
`data/config-repo/<device>/<timestamp>.cfg`

Optional secondary path:
`data/config-repo/<device>/latest.cfg`

## 14.3 Commit Strategy
A Git commit should occur only when config content changes for a device.

Commit message format:
`config snapshot: <device> <timestamp>`

The PRD should clarify whether this is:
- one commit per changed device
or
- one commit per collection cycle containing all changed device configs

Recommend:
**one commit per collection cycle with all changed configs included**, for cleaner global timeline correlation.

# 15. EVENT DETECTION MODEL

Phase 1 event detection should be rule-based and deterministic.

## Core Event Types
- CONFIG_CHANGE
- LATENCY_SPIKE
- PACKET_LOSS_INCREASE
- INTERFACE_DEGRADED
- CPU_RISE
- OUTAGE_STARTED
- OUTAGE_ENDED optional
- CORRELATION_FLAG

## Threshold Examples
These can be refined but should be explicit in the PRD.

### Config Change
Trigger:
- config_hash differs from previous snapshot

### Latency Spike
Trigger:
- latency exceeds threshold, e.g. > 50 ms
or
- latency increases by a multiplier over baseline

### Packet Loss Increase
Trigger:
- packet loss exceeds threshold, e.g. > 20%

### Interface Degraded
Trigger:
- oper state changes
or
- rx/tx errors exceed threshold relative to prior snapshot

### CPU Rise
Trigger:
- CPU increases beyond threshold, e.g. > 70%
or
- sharp relative jump between snapshots

### Outage Started
Trigger:
- packet loss reaches 100%
or
- latency exceeds outage threshold
or
- subnet reachability status for scenario becomes failed

The final PRD should choose one deterministic outage rule for Phase 1.

# 16. CORRELATION ENGINE

Phase 1 uses **rules-based suspicion**, not true causality inference.

## Goal
Highlight suspicious recent changes before the outage.

## Required Phase 1 Correlation Rules

### Rule A — Recent Config Change Before Degradation
If:
- CONFIG_CHANGE occurred on a device
- and LATENCY_SPIKE or PACKET_LOSS_INCREASE occurred within a defined window
Then:
- emit CORRELATION_FLAG

### Rule B — ACL-Related Suspicion
If:
- semantic diff shows new deny ACL entry involving scenario subnet
- and outage affects that subnet
Then:
- generate suspicion summary referencing ACL change

### Rule C — Time-Ordered Suspicion
If:
- config change precedes all major degradation events in the incident
Then:
- rank config change as primary suspicious event

## Required Correlation Output Style
The system should produce natural-language suspicion messages like:
- “A recent ACL change on edge-router-1 preceded latency degradation and outage for subnet 10.0.1.0/24.”
- “The new deny rule referencing 10.0.1.0/24 is likely related to the outage.”
